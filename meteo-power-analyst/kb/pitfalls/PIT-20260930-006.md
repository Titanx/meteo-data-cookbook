# 静止卫星的"延迟"与"体积"都有多个口径——不写口径的数字无法复核

> 最后更新: 2026-09-30
> 成熟度: **verified**（2026-09-30 对 GK2A / Himawari-9 / GOES-19 ABI / GLM 四个源做全天全量实测）
> 适用场景: 任何给卫星源写"延迟 X 分钟""单时次 Y MB"的地方；任何按延迟选源（"近实时该选谁"）的判断

## 1. 一个数字，四种口径

"延迟"在静止卫星上至少有四个互不相同的量，数值可以差 3~5 倍：

| 口径 | 定义 | 谁在用 |
|---|---|---|
| ① **标称时刻 → 落桶** | `S3 LastModified` − 目录名/文件名里的标称时刻 | 本文默认口径；可复核性最好 |
| ② **扫描结束 → 落桶** | ① − 扫描时长 | 直觉上的"这条数据多久能拿到" |
| ③ **最新可用时次滞后**（freshness） | 当前时刻 − 目录里最新那个时次的标称时刻 | "轮询时能看到多新的数据" |
| ④ **扫描时长本身** | 全盘成像需要的时间 | 常被忽略，但恰恰是①②之差 |

**关键点：①②③ 都"对"，但混用会得出完全不同的选源结论。**

## 2. 怎么一次拿到（不用守着轮询）

**S3 的 `LastModified` 就是对象的写入时刻**，一次 `ListObjectsV2` 列举即可拿到整时次（乃至整天）所有文件：

```python
# 一次列举 → 每个文件的 (Key, LastModified, Size) 全都有
GET https://<bucket>.s3.amazonaws.com/?list-type=2&prefix=<YYYY/MM/DD/HH>/&max-keys=1000
```

- 不需要轮询、不需要下载文件本身
- 标称时刻从 **Key 里正则抠**（各源位置不同，见 §4）
- ⚠️ 列举有 1000 条上限，**必须翻页到 `IsTruncated=false`**（见 `PIT-20260930-005`）

## 3. 实测（2026-09-29 全天，全量列举）

| 源 | 文件数 | ① 标称→落桶（最短/中位/P95/最长，分） | 扫描时长 | ② 扫描结束→落桶（分） |
|---|---|---|---|---|
| **GK2A** AMI FD | 2,272 | 21.3 / **23.2** / 38.7 / 42.4 | ≈9.1（实测） | 12.2 / **14.1** / 33.3 |
| **Himawari-9** AHI FLDK | 22,720 | 10.2 / **11.9** / 13.6 / 16.0 | ≈10 | 0.2 / **1.9** / 6.0 |
| **GOES-19** ABI RadF | 2,303 | 10.0 / **10.2** / 10.8 / 11.3 | ≈10（反推） | 0.0 / **0.1** / 1.3 |
| **GOES-19** GLM LCFA | 4,315 | 0.4 / **0.8** / 1.2 / 1.8 | 20 秒窗口 | ≈0 |

**读法**：

- **GK2A 的 23 分钟里有 9 分钟是它自己扫描**。改成②的口径只有 12~14 分，"慢"的印象一大半来自
  把扫描时长算进了传输。原文"东亚近实时不要选 GK2A"因此过重 ⇒ 应为
  **"GK2A 可作补充源，但按'单个文件就绪'来用"**（等某一条通道可用，而不是等整时次凑齐）。
- **GK2A 有双峰**：每个小时的 `:50` 时次稳定晚到 **41~42 分**（其余时次 21~27 分），
  按"整个时次到齐"判断会显得特别慢。**别用整时次齐备当判据。**
- **Himawari-9 的①中位 11.9 分几乎等于扫描时长 10 分** ⇒ 扫描一结束就入库，链路几乎零延迟。
- **GOES ABI 的②只剩 0~1.3 分（中位约 12 秒）**。所以"GOES 延迟 17~58 秒"和"GOES 延迟约 10.5 分钟"
  **是同一件事**——前者是②、后者是①。两者混排在同一张表里就会自相矛盾。
- **GLM 的 0.8 分是从 20 秒窗口起点算的**；从窗口结束算约 28 秒。原写"<20 秒"偏乐观。

## 4. 标称时刻藏在 Key 的哪儿

| 源 | 标称时刻来源 | 例子 |
|---|---|---|
| GK2A | 文件名末段 `_YYYYMMDDHHMM.nc` | `..._ir105_fd020ge_202609290610.nc` |
| Himawari-9 | **目录名** `YYYY/MM/DD/HHMM` | AHI-L1b-FLDK/2026/09/29/0610/ |
| GOES ABI / GLM | 文件名 `_sYYYYDDDHHMMSSS_`（**儒略日**） | `..._s20262720620...` |

GK2A 的语义可进一步用文件内属性钉死（实测）：
`mission_reference_time=20260929_061000`（标称）、`scene_acquisition_time=..._061032`（实际采集）、
`file_generation_time=..._061953`（生成，标称后 9.9 分）、`observation_start/end_time` 之差 = 543 s（扫描 9.1 分）。

## 5. 文件体积同样随时次变（必须标测量时次）

静止卫星的压缩率随**昼夜**（可见光/近红外通道白天有信号、夜间几乎全噪声）和**天气**（云/闪电密度）剧烈变化。

| 源 | 夜/静 | 昼/活跃 | 倍数 |
|---|---|---|---|
| GOES-19 ABI 全盘 16 通道 | **471.5 MB**（06Z 标称 :20） | **961.0 MB**（18Z） | 2.0× |
| 　└ C02（0.5 km） | 202.3 MB | 432.3 MB | 2.1× |
| 　└ C01（1 km，蓝） | **3.2 MB** | **84.7 MB** | **26×** |
| Himawari-9 全盘 160 文件 | 450 MB（12Z，东亚夜） | 742 MB（06Z，东亚午后） | 1.6× |
| 　└ B01 单波段 10 段 | 28.5 MB | 72.4 MB | 2.5× |
| GOES-19 GLM 单小时 | 53.9 MB（15Z 最静） | 112.2 MB（00Z 最活跃） | 2.1× |
| 　└ 单文件均值 | 0.300 MB | 0.627 MB | 2.1× |

⇒ **写"单时次 X MB"必须同时写测量时次**。只记一个夜间时次（如 GOES C01=17 MB）
再拿去做白天容量规划，会低估到 1/26。
另注：**"全波段 1.3 GB"这类数字要标压缩口径**——AWS 桶给的是已压缩文件，
实测 Himawari-9 全盘 16 波段 160 文件只有 450~742 MB（原文的 1.3 GB 偏大）。

## 6. 落地纪律

1. 写延迟先写清是①②③哪个；能复核的场合一律用 ①（标称→落桶），并给 **P95 与最长**，不只给中位
2. **不要用"整时次是否齐备"当延迟判据**（GK2A 的 `:50` 时次会把它拖到 42 分）
3. 写体积必须写**测量时次**（含 UTC 时刻），并尽量给昼夜两端各一个数
4. 选源结论（"近实时选谁"）要把**扫描时长**扣掉再比，否则会把卫星自身的成像时间算成分发延迟
