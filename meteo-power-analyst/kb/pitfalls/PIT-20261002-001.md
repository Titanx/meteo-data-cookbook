# 裸域被 DNS 屏蔽 + 边缘 IP 池 + 单连接限速 + 链路挂死：Zenodo 批量下载的五重坑

> 最后更新: 2026-10-02
> 成熟度: **verified**（2026-10-02 实测 Kelmarsh 记录 16807551，15 个文件 / 3.84 GB）
> 适用场景: 从 Zenodo（及同类"裸域被屏蔽、内容托管在小对象存储"的站点）批量下载大文件

## 1. 五个独立的问题，症状完全不同

| # | 问题 | 症状 | 误判方向 |
|---|---|---|---|
| ① | **裸域被 DNS 屏蔽** | `zenodo.org` 解析到 `0.0.0.0`；curl 返回 `http=000`；JSON 解析直接爆 `JSONDecodeError` | 以为是"网站挂了"或"API 改版" |
| ② | **边缘 IP 池里混着坏 IP** | 同一个 `www.zenodo.org` **每次解析到的 IP 不同**，有的直接连不上（`http=000`）、有的限速、有的流畅 | 以为"时快时慢是网络抖动" |
| ③ | **单连接被限速，多连接可叠加** | 单连接只有 0.1–1 MB/s，而同一台机器从 GitHub 能跑 **7 MB/s**；并发多连接总吞吐明显更高 | 以为"本机带宽就这样" |
| ④ | **部分并发被限流** | 并发数开太大时出现 **0 字节 `.part`**，且长期不增长 | 以为是"文件不存在"或"磁盘满" |
| ⑤ | **链路中途挂死 / 速率塌陷** | 文件下到一半**长时间不再增长**，或速率从 0.5 MB/s 悄悄掉到 0.035 MB/s 而不报错 | 以为是"下载慢"，于是一直等 |

五者叠加时最容易被笼统归因为"网络太慢"，实际是**不同的故障**，要分别应对。

## 2. ① DNS 屏蔽：裸域假死、www 别名正常

**实测（本机）**：

| 主机名 | 解析结果 | 可用 |
|---|---|---|
| `zenodo.org` | **0.0.0.0** | ❌ |
| `www.zenodo.org` | 真实 IP（实测出现过 `137.138.153.219`、`188.184.103.118`，随 CDN 变化） | ✅ |
| `archive.org` | 指向 Facebook 的 IP | ❌ |
| Cloudflare DoH（`1.1.1.1`） | 请求被阻断 | ❌（无法靠 DoH 自救） |

**关键判据**：裸域返回 `0.0.0.0`（或明显错误的 IP），但**加 `www.` 就能拿到真实 IP**
⇒ 这不是"站点宕机"，而是**本机 DNS 对特定主机名的屏蔽**。

**绕行**：不要改脚本里的 URL（API 返回的链接就是裸域），改为在**进程内给 `socket.getaddrinfo` 打别名补丁**，
把裸域指向 `www.` 的 IP。TLS 的 SNI 与证书校验仍按原主机名进行，不受影响：

```python
def patch_dns() -> str:
    orig = socket.getaddrinfo
    ip = orig("www.zenodo.org", 443, type=socket.SOCK_STREAM)[0][4][0]
    def patched(host, *a, **kw):
        if host in ("zenodo.org", "www.zenodo.org"):
            port = a[0] if a else kw.get("port", 443)
            return [(socket.AF_INET, socket.SOCK_STREAM, 6, "", (ip, port))]
        return orig(host, *a, **kw)
    socket.getaddrinfo = patched
    return ip
```

## 3. ② 并发限流：并行下载反而更慢

**实测**：同时起多个 Python 进程各下一个文件 → 若干文件出现 **0 字节 `.part`** 并停滞；
杀掉多余进程、改回**单进程串行**后，同一批文件恢复正常增长。

**纪律**：单文件并发段数不要开太大（**实测 4 段可用，6 段会全线 0 字节**）。

## 4. ② ③ 边缘 IP 池 + 单连接限速：镜像思路是"选 IP + 分段并发"

**② 边缘 IP 池**：`www.zenodo.org` 解析到的是 CERN 的一组边缘 IP，**每次解析结果不同**，
而且质量差异极大。实测一次全量探测（同一时刻、单连接、3 MB Range）：

| IP | 结果 |
|---|---|
| `188.185.48.75` | **1.07 MB/s** |
| `188.184.103.118` | 0.64 MB/s |
| `137.138.52.235` / `137.138.153.219` | 0.42–0.43 MB/s |
| `188.185.43.22` / `137.138.6.45` / `188.184.106.84` / `137.138.24.6` | **`http=000`（完全连不上）** |

⇒ **不能信任一次 DNS 解析**：要在启动时对候选 IP 逐个测速、选最快的（脚本里的 `pick_ip`）。
若恰好解析到坏 IP，会表现为"整个站点不可用"，极易误判为封禁。

**③ 单连接限速、多连接可叠加**：同一台机器从 GitHub 能跑 **7.2 MB/s**，
而 Zenodo 单连接只有 0.1–1 MB/s ⇒ 瓶颈在服务端**按连接/按 IP 限速**，不是本机带宽。
实测把文件切成 4 段并发取，能把 473 MB 的年包在 **108 s** 内下完（**4.4 MB/s**），
而单连接同一时段只有 ~0.1 MB/s ⇒ **约 40 倍**差距。

**结论**：对这类站点，正确的加速姿势是 **① 选最快边缘 IP + ② 分段并发（每段一条连接、各自 Range + 重试 + 单独校验长度）**，
最后按段序合并并核对总长；而不是"换成单进程慢慢等"。

## 5. ④ ⑧ 链路挂死 / 速率塌陷：超时要压短，不是加长

**两种坏形态**：

| 形态 | 表现 | 判据 |
|---|---|---|
| 截断 | 文件比声明体积小（实测 `Kelmarsh_Grid_Meter`：**1,713,896 vs 1,723,178**，差 9,282 B） | 体积不等于 API 声明的 `size` |
| 挂死 | 文件长时间**字节数不变**（实测 2018 年包卡在 **2,097,152 B** 不动超过 3 分钟） | 进程存活、CPU 近 0、文件不再增长 |
| 速率塌陷 | 连接不死、也不报错，速率从 0.5 MB/s 掉到 **0.035 MB/s** | 按 30s 窗口算速率，低于阈值就主动断开重连 |

**反直觉的修法**：读超时**从 300s 压到 45s**。挂死的连接不会自己恢复，
超时越短越早触发重连，配合 `.part` 续传**反而更快**。加长超时只会让整轮卡死更久。
另加**低速看门狗**（30s 窗口内速率低于 0.2 MB/s 且剩余量还大 → 断开重连），专治"不死但塌陷"。

**续传的两个前提**（缺一不可）：

1. 服务端支持 `Range`（返回 `206`）
2. **重定向后 `Range` 仍生效** —— 若返回 `200`（忽略 Range），必须**从头重写**（`wb` 截断），
   否则会新旧拼接连成体积错误或内容错乱的假文件

```python
with urllib.request.urlopen(req, timeout=45) as r:
    if have and r.status != 206:   # 服务端忽略 Range → 丢弃旧片段重来
        have = 0
    with open(part, "ab" if have else "wb") as f:
        ...
```

**重试纪律**：重试次数要给够（实测 8 次、退避 `5*(k+1)` 秒），单次失败不能判定整体失败。

## 6. 落地纪律

1. 遇到 `0.0.0.0` / `http=000`，先做**裸域 vs `www.` 别名**对照，再决定是换源还是打 DNS 补丁
2. **不要信任一次 DNS 解析**：把候选 IP 全测一遍再选最快的，坏 IP 会伪装成"站点被墙"
3. **先判断瓶颈在谁**：拿同一台机器试一个已知快的源（如 GitHub），就能区分"本机带宽差"与"对端限速"
4. 对端限速时，正确做法是**分段并发**（每段独立 Range + 重试 + 长度校验 + 按序合并），不是"单进程慢慢等"
5. 并发段数要适中：**4 段可用，6 段会被打到 0 字节**
6. 大文件下载器必须同时具备：`.part` 续传 + **45s 短读超时** + **低速看门狗** + **体积校验** + **多次重试**
7. 用"体积是否等于 API 声明值"作为完成判据，不要以"脚本退出码为 0"为准

## 真实案例

2026-10-02 ~ 10-03 下载 Kelmarsh 风电场数据集（Zenodo 记录 16807551，15 文件 / 3.84 GB）：
前 1.2 GB 用"单连接串行 + 续传"跑了约 2 小时（均速 ~0.3 MB/s），诊断出瓶颈后改造为
"选最快边缘 IP + 4 段并发"，**剩余约 2.6 GB 只用 8.6 分钟**（均速 7.4 MB/s）下完。

| 阶段 | 现象 | 处置 |
|---|---|---|
| 首次 | curl `http=000`、API JSON 解析失败 | 确认裸域→`0.0.0.0`，`www.`→真实 IP；打 `getaddrinfo` 补丁 |
| 并发期 | 多进程 → 多个 0 字节 `.part` | 收敛并发度，改单文件多段并发 |
| 串行期 | `Grid_Meter` 少 9,282 B | 加体积校验 + 重试 |
| 串行期 | 2018 年包卡在 2,097,152 B 不动 | 读超时 300s→45s，续传恢复 |
| 串行期 | 速率从 0.5 MB/s 塌陷到 0.035 MB/s | 加低速看门狗（30s 窗口） |
| 诊断 | GitHub 7.2 MB/s vs Zenodo 单连接 0.1 MB/s | 定位为对端按连接限速 |
| 改造 | 8 个候选 IP 测速，最慢/最快差 10 倍且 4 个连不上 | `pick_ip()` 选优 |
| 改造 | 4 段并发 | 473 MB / 108 s = **4.4 MB/s** |
