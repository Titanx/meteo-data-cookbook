# 裸域被 DNS 屏蔽 + 并发限流 + 链路挂死：Zenodo 批量下载的三重坑

> 最后更新: 2026-10-02
> 成熟度: **verified**（2026-10-02 实测 Kelmarsh 记录 16807551，15 个文件 / 3.84 GB）
> 适用场景: 从 Zenodo（及同类"裸域被屏蔽、内容托管在小对象存储"的站点）批量下载大文件

## 1. 三个独立的问题，症状完全不同

| # | 问题 | 症状 | 误判方向 |
|---|---|---|---|
| ① | **裸域被 DNS 屏蔽** | `zenodo.org` 解析到 `0.0.0.0`；curl 返回 `http=000`；JSON 解析直接爆 `JSONDecodeError` | 以为是"网站挂了"或"API 改版" |
| ② | **并发被限流** | 多进程各自下载 → 出现 **0 字节 `.part`**，且长期不增长 | 以为是"文件不存在"或"磁盘满" |
| ③ | **链路中途挂死** | 文件下到一半**长时间不再增长**（socket 收不到数据也不报错） | 以为是"下载慢"，于是一直等 |

三者叠加时最容易被误判为"网络太慢"，实际是**三个不同的故障**，要分别应对。

## 2. ① DNS 屏蔽：裸域假死、www 别名正常

**实测（本机）**：

| 主机名 | 解析结果 | 可用 |
|---|---|---|
| `zenodo.org` | **0.0.0.0** | ❌ |
| `www.zenodo.org` | 真实 IP（实测出现过 `137.138.153.219`、`188.184.103.118`，随 CDN 变化） | ✅ |
| `archive.org` | 指向 Facebook 的 IP | ❌ |
| Cloudflare DoH（`1.1.1.1`） | 请求被阻断 | ❌（无法靠 DoH 自救） |

**关键判据**：裸域返回 `0.0.0.0`（或明显错误的 IP），但**加 `www.` 就能拿到真实 IP**
⇒ 这不是"站点宕机"，而是**本机 DNS 对特定主机名的屏蔽**。

**绕行**：不要改脚本里的 URL（API 返回的链接就是裸域），改为在**进程内给 `socket.getaddrinfo` 打别名补丁**，
把裸域指向 `www.` 的 IP。TLS 的 SNI 与证书校验仍按原主机名进行，不受影响：

```python
def patch_dns() -> str:
    orig = socket.getaddrinfo
    ip = orig("www.zenodo.org", 443, type=socket.SOCK_STREAM)[0][4][0]
    def patched(host, *a, **kw):
        if host in ("zenodo.org", "www.zenodo.org"):
            port = a[0] if a else kw.get("port", 443)
            return [(socket.AF_INET, socket.SOCK_STREAM, 6, "", (ip, port))]
        return orig(host, *a, **kw)
    socket.getaddrinfo = patched
    return ip
```

## 3. ② 并发限流：并行下载反而更慢

**实测**：同时起多个 Python 进程各下一个文件 → 若干文件出现 **0 字节 `.part`** 并停滞；
杀掉多余进程、改回**单进程串行**后，同一批文件恢复正常增长。

**机制**：Zenodo 按来源 IP 限制并发连接数，超限的连接被接受但不给数据（表现为 0 字节）。
并行下载**不会更快**，只会让所有连接一起卡住。

**纪律**：Zenodo 及同类站点**一律单进程串行 + 断点续传**，不要用多进程/多线程"加速"。

## 4. ③ 链路挂死：超时要压短，不是加长

**两种坏形态**：

| 形态 | 表现 | 判据 |
|---|---|---|
| 截断 | 文件比声明体积小（实测 `Kelmarsh_Grid_Meter`：**1,713,896 vs 1,723,178**，差 9,282 B） | 体积不等于 API 声明的 `size` |
| 挂死 | 文件长时间**字节数不变**（实测 2018 年包卡在 **2,097,152 B** 不动超过 3 分钟） | 进程存活、CPU 近 0、文件不再增长 |

**反直觉的修法**：读超时**从 300s 压到 45s**。挂死的连接不会自己恢复，
超时越短越早触发重连，配合 `.part` 续传**反而更快**。加长超时只会让整轮卡死更久。

**续传的两个前提**（缺一不可）：

1. 服务端支持 `Range`（返回 `206`）
2. **重定向后 `Range` 仍生效** —— 若返回 `200`（忽略 Range），必须**从头重写**（`wb` 截断），
   否则会新旧拼接连成体积错误或内容错乱的假文件

```python
with urllib.request.urlopen(req, timeout=45) as r:
    if have and r.status != 206:   # 服务端忽略 Range → 丢弃旧片段重来
        have = 0
    with open(part, "ab" if have else "wb") as f:
        ...
```

**重试纪律**：重试次数要给够（实测 8 次、退避 `5*(k+1)` 秒），单次失败不能判定整体失败。

## 5. 落地纪律

1. 遇到 `0.0.0.0` / `http=000`，先做**裸域 vs `www.` 别名**对照，再决定是换源还是打 DNS 补丁
2. Zenodo 类站点**只单进程**，不要并行
3. 大文件下载器必须同时具备：`.part` 续传 + **45s 短读超时** + **体积校验** + **多次重试**
4. 用"体积是否等于 API 声明值"作为完成判据，不要以"脚本退出码为 0"为准
5. 并行下载一处卡住就先怀疑限流，不要先怀疑带宽
