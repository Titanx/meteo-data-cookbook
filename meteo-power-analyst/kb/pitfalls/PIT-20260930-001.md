# 凭据硬编码与原始材料层外泄：`.gitignore` 挡不住脚本里的明文口令

> 最后更新: 2026-09-30
> 成熟度: **verified**（本项目实测，已定位到已推送的引入提交并完成脱敏与整改）
> 适用场景: 任何"边研究边记流水"的仓库——尤其会把会话摘要、研究过程原文一并归档的项目

## 1. 现象（本项目实测）

`.env` 早已被 `.gitignore` 忽略、也从未进过 git，但仓库里仍有两类真实凭据溜了出去：

| 泄漏形态 | 位置 | 状态 |
|---|---|---|
| 明文账号 + 口令 | `skills/data-fetch-satellite/references/test_cma_api.py` 顶部的裸变量赋值（旧仓库同路径副本亦有） | **已推送到远端**（引入提交 `fe07bba`） |
| API key 被原文转述 | 原始材料层的会话记忆与由其汇总的话题档案 | 只在未推送提交里，已脱敏并整层排除版本库 |

两类**都不是** `.env` 泄漏，所以"我已经加了 .gitignore"这个直觉判断在这里完全失效。

## 2. 为什么危险

1. `.gitignore` 只保护**文件**，不保护**文件里写的内容**——脚本、笔记、会话摘要都可能原样转述凭据
2. 归档流水账时最容易出事：会话摘要会把"当时用了哪个 key"当成事实忠实记下，越忠实越危险
3. 一旦推送，**回滚 ≠ 撤回**：远端已有副本、可能已被抓取；删提交只是让本地看不见

## 3. 排查信号

- 只看 `.env` 有没有被忽略 → 不够。必须做**值级比对**：把 `.env` 里的值当已知串，在已跟踪文件里精确搜
- 形态扫描**必须覆盖裸变量名**：`USER` / `PWD` / `USERID` / `EMAIL` / `APPKEY` / `ACCESS_KEY`。
  只搜 `password` / `token` 会正好漏掉 `PWD = "..."` 这种写法——本项目就是这么漏的
- 判定"是否已外泄"用两条命令：`git log --all -S<值>` 找引入提交，`git grep <值> origin/main` 确认远端有没有

## 4. 处置（按优先级）

1. **先轮换凭据，再谈清理**——已推送的凭据一律视为已泄露
2. 明文处改为读环境变量，缺失时直接报错退出（不要留内置默认值）
3. 把"整类会转述原文的材料"**整体**排除版本库（本项目把 raw/ 层整层加入 `.gitignore`），
   而不是逐个文件打补丁——自由文本无法保证穷尽
4. 提交前跑凭据闸门 `skills/kb-capture/references/secret_scan.py`
5. 是否重写历史 + 强推：若仓库公开，价值有限（副本已散出），**轮换才是有效补救**

## 5. 反面教训：别把摘要哈希当密钥

会话记忆里每条记录都带一个 `summary_digest`（64 位十六进制）。把"长十六进制"一律当密钥会刷屏误报，
最后没人再看告警。形态识别要收窄，**主力检查交给 `.env` 值级比对**（零误报）。
