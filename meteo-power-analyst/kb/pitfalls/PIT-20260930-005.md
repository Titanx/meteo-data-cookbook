# S3 分页静默截断：把「单次列举 1000 条的上限」误当成「归档止于某日」

> 最后更新: 2026-09-30
> 成熟度: **verified**（2026-09-30 由第三方独立验证发现，本项目逐项复现到根因）
> 适用场景: 任何用 S3 `ListObjectsV2` 判断"某归档覆盖到哪天/有没有数据"的工作，
> 尤其是**否定性结论**——"数据没有了""归档终止了""只有这一段时间"

## 1. 现象

条目 `recipes/RCP-20260927-001` 曾写：MRMS 降水的 S3 归档 **止于 2023-07-10**，
"每个产品恰好 1000 天，官方已停止写入"，并据此给出结论"批量历史回补只能取 2020-10-14 ~ 2023-07-10"。

**实测（2026-09-30）**：该归档共 **2,178 个日期目录**，最新日 = 当天；
2023-07-11 / 2024 / 2025 / 2026-09-28 **都有文件**。归档一直在写。

关键提示：**2020-10-14 到 2023-07-10 恰好 1000 天** —— "恰好 1000"这个数字本身就是分页边界的指纹。

## 2. 根因（两个缺陷叠加，缺一不可）

本项目直接跑原始脚本的 `list_archive_dates()` 复现：

```
第 1 页: 本页 1000 条, 继续翻页
第 2 页: 本页 0 条, 循环退出
总日期数 1000   最新 .../20230710/
```

1. **手拼 URL 未对 `continuation-token` 做 URL 编码**。该 token 是 base64 风格字符串，**含 `/`（也常见 `+`）**；
   未编码时 S3 直接拒绝：

   ```
   HTTP 400  <Error><Code>InvalidArgument</Code>
             <Message>The continuation token provided is incorrect</Message>
             <ArgumentName>continuation-token</ArgumentName>
   ```

2. **不检查 `status_code`，且把"响应里没有 `NextContinuationToken`"当成"取完了"**。
   400 的错误体里自然没有 `<Prefix>` 也没有 `<NextContinuationToken>` ⇒ 循环正常退出、
   返回"干净"的第一个 1000 条，**没有任何报错**。

⇒ 页 2 的失败被伪装成"数据到此为止"。**这是"不报错的错"的典型**：函数返回了结果、
数据也非空、量纲也对，只是少了 1,178 天。

## 3. 排查信号

- **条目里的日期区间恰好是 1000 天 / 1000 条 / 10000 条这类整数** → 先怀疑分页，而不是"官方停更"
- 分页函数的第 N 页数量突然为 0 而 `IsTruncated` 却是 `false`
- 手拼的 URL 里带有从响应里抠出来的 token、签名、游标（未编码）
- 否定性结论（"没有了""终止了""为空"）**只跑过一次、没有换一种方式复核**

## 4. 绕行方案

1. **让库做编码**：`requests.get(url, params={...})`（本项目修正后 3 页 `[1000, 1000, 178]` 一次取全）
2. **必须校验 `status_code`**，非 200 直接抛错；不要对错误体做正则
3. **收尾判定只看 `IsTruncated`**：缺这个字段就报错，不要默认"结束了"
4. **否定性结论要加强证据**：额外取一个"应当有数据"的具体日期做点查（例如 2024-01-15 的某个 key 是否存在），
   或换一种列举方式交叉验证
5. 归档类结论写进条目时，注明**列举方式与页数**（本项目现在写"3 页、2178 天、`IsTruncated=false` 收尾"）

## 5. 真实案例

| 项 | 内容 |
|---|---|
| 桶/前缀 | `noaa-mrms-pds` /（前缀）CONUS/MultiSensor_QPE_01H_Pass2_00.00/ |
