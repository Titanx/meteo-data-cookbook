# 同一段 NASA POWER 辐照会换版本：先以 FLASHFlux 发布，之后被 SYN1deg 覆盖

> 最后更新: 2026-09-30
> 成熟度: **verified**（API 原样复现）
> 适用场景: 拼接 NASA POWER 长序列、用最近几个月数据做滚动验证、声明"辐照延迟 3–4 个月"

## 1. 坑的描述

NASA POWER 的辐照**不是一次性定版**：最近几个月的辐照先以近实时产品 **FLASHFlux** 发布，
等 CERES 正式产品 **SYN1deg** 出来后再被**覆盖**。后果有两个：

1. **同一天的数据会变**——同一个 `start/end` 在 2026-08 请求和在 2026-12 请求，
   拿到的可能是两个不同版本的辐照值；拼长序列时前后**不是同一个版本**，水平/趋势会出现台阶。
2. **FLASHFlux 只填 daily，hourly 不填**——这一点最容易误判。

## 2. 实测证据（2026-09-30，点位 lat 31.5 / lon −102.5，`header.sources`）

| 请求 | sources | 辐照缺测 |
|---|---|---|
| daily 2026-05-15 / 06-15 | `SYN1DEG` | 0 |
| daily 2026-07-15 / 08-15 | `FLASHFLUX` | 0 |
| daily 2026-09-10 | `FLASHFLUX` | 0 |
| **hourly 2026-08-15** | `SYN1DEG, MERRA2` | **24/24 全 = −999** |
| **hourly 2026-09-20** | `SYN1DEG, GEOSIT` | **24/24 全 = −999** |
| hourly 2025-07-01 | `SYN1DEG, MERRA2` | 0 |

⇒ 2026-07 起进入 FLASHFlux 窗口，但**只对 daily 生效**：同一天的 daily 有辐照值、
hourly 全缺测。所以"某天 daily 有辐照"**推不出**"那天 hourly 也有"。

## 3. 排查信号

- 同一 `date` 两次请求的 `header.sources` 不同（SYN1DEG ↔ FLASHFLUX）
- daily 有值而 hourly 全是 −999（不是"数据还没到"，而是"hourly 不走 FLASHFlux 通道"）
- 长序列在最近几个月出现台阶，或最近几个月的月能量与历史同期系统性偏离
- 报告里写"辐照延迟 3–4 个月"却又能拿到上个月的值 → 那是 FLASHFlux，不是 SYN1deg

## 4. 绕行方案

1. 取数时同时记录 `header.sources` 与**请求日期**，让数据自带"版本 + 快照时间"
2. 跨 FLASHFlux/SYN1deg 边界的序列二选一：① 截断到 SYN1deg 覆盖区（保守，推荐做趋势）；
   ② 保留但显式声明版本切换点，且不跨边界做同质性假设
3. 需要 hourly 的历史覆盖时，不要指望 FLASHFlux 补齐，直接接受"近 3–4 个月 hourly 辐照为空"
4. 滚动验证（近月样本外）若用了 FLASHFlux，结论要标注"近实时版"，正式版出来后应复核
