# ERCOT 月度增量刷新 SOP（市场侧刷到月末 → 合并去重 → 链条重算）

> 最后更新: 2026-10-03
> 成熟度: **verified**（2026-10-03 实跑，目标「数据到 2026-09-30」）
> 适用场景: ERCOT 电价 / 发电 / 负荷链路及其派生（缺口、弹性、指纹、可逆性）的**月度**刷新

## 0. 结论速览

- **市场侧能刷到月末**：EIA 月度 + GridStatus SPP 都跟得上；实测把 142 个
  `(market, location)` 并成单文件全期序列，枢纽/LZ 覆盖到 `2026-10-01`（左闭右开 = 含 9/30 全天）
- **分析链的上限由最慢的输入决定，不是由面板决定**（本次最大的认知修正）：
  | 链路 | 输入 | 本次可达上限 |
  |---|---|---|
  | 面板 / 价格弹性 / 持续时长 / 口径对比 | EIA 月度 + RTM/DAM | **2026-09-30** ✓ |
  | 风功率潜力与缺口 | HRRR 80m 风速（Open-Meteo，可延长） | **2026-09-30** ✓ |
  | 物理晴空反事实缺口 | HRRR 2m 气温（Open-Meteo，可延长） | **2026-09-30** ✓ |
  | 全天候光伏潜力（内生缺口） | NASA POWER 小时辐照 | **2026-06-30** ✗（源侧延迟） |
  | 光伏格参与的指纹 / 可逆性检验 | 同上 | 随之上限 6/30 |
- **NASA POWER 小时辐照约有 3 个月发布延迟**：2026-10-03 实测「有值止于 2026-06-30」，
  2026-07-01 起 `ALLSKY_SFC_SW_DWN` 整段返回 `-999`（键存在、值为填充）。
  只测有/无键会误判为"有数据"；必须看**值的填充率**。
  查法：`(a <= -900).mean()`，或逐日均值；当年的 npz 若在 7 月后全 NaN，就是这个原因。
- **GridStatus 免费额度是「按自然月」重置**（`current_usage_period_start` = 月初）：
  250 请求 / 500k 行。一次全量刷新（含枢纽+LZ+120 节点）约 170 请求 / 340k 行
  ⇒ 一个月基本只够一次全量，别把额度花在逐点补数上（见第 3 步的批量写法）。

## 3. 补边界日：一次请求补多个结算点

跨两次请求的边界日（本次是 9/7 与 9/30）会漏。补的时候**不要逐点**：

```python
df = client.get_dataset("ercot_spp_real_time_15_min",
                        start="2026-09-07", end="2026-09-30",
                        filter_column="location", filter_value=[<一串节点>],
                        filter_operator="in",   # ⚠️ 必须 in；默认 = 只会匹配一个
                        verbose=False)
```

实测：128 个节点 × 2 个窄窗口（9/7、9/30）= **8 次请求 / 2.4 万行**；逐点则要 256 次。

## 4. 合并去重（每次刷新必做）

按 `(market, location)` 把同目录所有 `ercot_{rtm,dam}_{loc}_<起>_<止>.csv`
合成**单文件全期序列**：键 `interval_start_utc`，按（起始日, 结束日）排序、**新块覆盖旧块**，
旧 chunk 移入 `_merge_backup_<日期>/`。

- 本次 141 组需要合并、重叠 66,808 行、**值冲突 0 行**（去重安全）
- 输出报告：重叠行数 + 值冲突数 + 时间轴缺口（用众数步长判缺口）
- 留下的**真实源空洞**要单独记：本次 4 个 30 分钟洞（1/8、6/4、7/9、8/27 的 15min 段），
  与"请求边界漏日"性质完全不同，不要试图重下

**同时**把下游脚本里**硬编码的带日期文件名**改成 glob 解析（`ercot_rtm_HB_HOUSTON_*.csv`），
否则下次刷新又要改一遍；并在解析处断言"恰好 1 个文件"。

## 5. 天气侧输入（想让链条到月末就必须做）

| 输入 | 脚本 | 能否延长 | 做法 |
|---|---|---|---|
| HRRR 80m 风速（165 点） | `download_hrrr_wind_2025_2026.py` | ✅ | 改 `END` 或**增量追加** |
| HRRR 2m 气温（141 点） | `download_hrrr_temp_2025_2026.py` | ✅ | 同上 |
| NASA POWER 辐照（136 点） | `download_nasa_power_ercot_pv.py` | ❌ 源侧延迟 | 只能等；不要用填充值硬拼 |

- 三个下载脚本都是**全量重写**型（改 `END` 重跑要从 2025-01-01 起重下 600+ 天）：
  实测 HRRR 逐批（20 点/请求）约 16 min/文件，NASA 逐点约 8 min ⇒ 全量重跑 ~40 min
- **更优做法是增量追加**：只拉新增窗口，按旧 `.npz` 里已保存的坐标/顺序对齐后 `vstack`。
  实测 HRRR 两个文件各约 2 min（0.75 s/点），且**不重写既有历史**
  （避免上游档案回溯变更污染旧段）
- ⚠️ 写增量脚本时两个坑：① 拼接前用旧 npz 的 `names` / `lat,lon` 驱动取数，保证顺序一致；
  ② **不要在同一进程里既 `np.load(同一路径)` 又 `np.savez_compressed(同一路径)`**——
  懒加载句柄会在文件被重写后失效（`BadZipFile: Bad magic number`）。先全部读进内存再写
