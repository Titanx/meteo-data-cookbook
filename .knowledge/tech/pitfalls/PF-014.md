# [PF-014] ENTSO-E / IEC 62325 报文的两处隐藏结构：curveType=A03 压缩 与 A01/A07 合约混装

> **类型**: pitfall
> **成熟度**: verified
> **创建时间**: 2026-09-29
> **最后引用**: 2026-09-29
> **标签**: entsoe, transparency-platform, iec62325, xml, curvetype, a03, variable-sized-block, forward-fill, contract-market-agreement, a01, a07, day-ahead, intraday, parsing, silent-data-loss, spain
> **适用阶段**: implement, verify, debug

## 背景

按 PS-036 从 ENTSO-E 拉西班牙日前电价（A44, 2024-04），解析后得到 **573 行**，而 4 月应有 **744 行**（31 天 UTC 窗口 × 24 h）。逐日点数在 9~21 之间不等，看起来像大规模缺数据——但实际上是 IEC 62325 的**变长块压缩表示**被误读。

修好压缩问题后又发现第二处隐藏结构：2026-01 的同一时刻出现 **3 个不同价格**，根因是报文**同时混装了 A01（日前）与 A07（日内）两个合约**。两处都会静默污染数据，故合并记录。

## 陷阱一：curveType=A03 变长块压缩 —— 缺失的 position 不是缺数据

### 现象

A44 2024-04 原始报文解析后：

| 天 | 显式 `Point` 数 | 应有槽位 |
|---|---|---|
| 2024-04-01 | 15 | 24 |
| 2024-04-02 | 20 | 24 |
| 2024-04-03 | 18 | 24 |
| 2024-04-04 | 15 | 24 |
| 2024-04-05 | 14 | 24 |
| … | 9~21 | 24 |
| **合计** | **573** | **744** |

第 1 天的 `position` 序列是 **1, 2, 3, 7, 8, 9, 10, 11, 15, 18, 20, 21, 22, 23, 24** —— 缺失 4/5/6、12/13/14、16/17、19。

### 根因

`TimeSeries` 里写着 **`<curveType>A03</curveType>`**。

IEC 62325 的 `curveType` 语义：

| 代码 | 含义 | 含义 |
|---|---|---|
| **A03** | **Variable sized block** | **每个 Point 的值一直延续到下一个 Point 之前**；连续相同的值被折叠成一个点 |
| A01 | Production/consumption point | 每个 Point 是独立的单点值，缺失 position 就是真缺 |

验证第 1 天：`pos3=0`，下一个点是 `pos7=0.13` ⇒ **4/5/6 三个小时都是 0**（被折叠）；`pos11=0`→`pos15=-0.01` ⇒ 12/13/14 都是 0；`pos18=0`→`pos20=0.44` ⇒ 19 是 0。缺口全部对应"与上一个点同值"。

**同一机制解释了两个旁证**：
1. A75（分技术实际发电）里，燃煤（B02）、油页岩（B07）等技术只有 **1 个 Point** —— 不是只有一个时刻，而是**整月恒定**。
2. A75 的 `B01`（生物质）2353 点 vs `B12`（库容水电）2851 点 —— 点数差异来自各自的重合折叠程度，不代表数据完整度。

### 影响（为什么是"静默"陷阱）

- 直接按显式 `Point` 落库 ⇒ **丢掉 20%~35% 的小时**，而且丢的是**低价格/零价格/恒定出力**时段。
- 对本项目尤其致命：西班牙负价恰好在 **0 元至负值**附近发生，而 0 值正是被折叠最多的那一类 ⇒ 会**系统性抹掉负价/零价小时**，把 PS-035 的负价概率直接压低。
- 不报错、不告警，行数看起来"只是少一点"，极易被当成正常缺测放过。

### 正确解析

```python
# 读 curveType；A03（或缺省）⇒ 前向填充展开到整段
expand = curve in ("A03", None)
n_slots = round((pd.Timestamp(end) - pd.Timestamp(start)).total_seconds() / step.total_seconds())
if expand:
    last = None
    for p in range(1, n_slots + 1):
        if p in pts:            # pts: {position: (value, tag)}
            last = pts[p]
        if last is None:
            continue            # 段首缺 Point（罕见）留空
        emit(t0 + step * (p - 1), last)
else:                           # A01 等：缺失即真缺
    for p in sorted(pts):
        emit(t0 + step * (p - 1), pts[p])
```

关键点：

1. **`n_slots` 必须由 `timeInterval` 的 start/end 与 `resolution` 算出**，不能用 `max(position)` —— 末段若整体被折叠，`max(position)` 会偏小。
2. **`resolution` 要按 `PT1M/PT5M/PT15M/PT30M/PT60M` 解析**（西班牙 A44 是 `PT60M`，A75/A65 是 `PT15M`）。
3. **时间戳一律是 UTC**（报文里 `start` 带 `Z`）；`periodStart=202404010000`（布鲁塞尔本地）对应报文里的 `2024-03-31T22:00Z`，换算不要漏。
4. **去重键要带维度**：A75 同一时间戳有多条技术序列，按 `datetime_utc` 单键去重会把多技术压成一条 ⇒ 必须按 `["datetime_utc", "psr_type"]`。

### 避坑建议（陷阱一）

1. 解析 ENTSO-E / IEC 62325 报文前，**先检查 `curveType`**，并至少对一个已知窗口做行数核对（如"4 月应 ≈ 744 小时"）。
2. 展开后做**完整性断言**：`实际槽位数 / 期望槽位数` 应接近 1；本流程展开后 2024-04 = 744/744。
3. 若关心低价/负价时段，**必须展开**——折叠掉的正是这些点。
4. 单元测试要专门覆盖**稀疏 position** 与前向填充，不能只测稠密报文（稠密报文下错误解析看起来完全正常）。

## 陷阱二：A44 同时返回 A01（日前）与 A07（日内）两套价格

### 现象

2026-01 的 A44 报文里有 **123 个 `TimeSeries`**，解析后 10,320 行但只有 **3,072 个唯一时刻** —— 每个 15 分钟槽位出现约 3 次。
同一时刻的 3 条记录**值还不同**：`mRID=1 → 112.01`、`mRID=2 → 93.22`、`mRID=3 → 91.31`（仅 22/3072 个时刻三条值恰好相同）。

**所有这些 TimeSeries 的 `in_Domain`/`out_Domain`/`businessType`/`resolution` 完全相同**（都是 `10YES-REE------0` / `A62` / `PT15M`），靠域名或分辨率无法区分。

### 根因

真正的区分字段是 **`contract_MarketAgreement.type`**：

| 代码 | 含义 | 2026-01 序列数 |
|---|---|---|
| **A01** | **Day ahead（日前）** | **32**（每天 1 段，覆盖 24 h） |
| **A07** | **Intraday（日内）** | **91**（每天 2~3 段，含 12 h 段） |

**时间线（实测各月）**：

| 期间 | TimeSeries | 合约 | 分辨率 |
|---|---|---|---|
| 2023-01 ~ 2025-08 | 29~32 | **仅 A01** | PT60M |
| **2025-09** | 111 | A01 31 + **A07 80** | PT15M + PT60M（切换月） |
| 2025-10 ~ 2026-09 | 112~125 | A01 29~32 + A07 83~93 | PT15M |

⇒ **A07 从 2025-09 起才出现**。所以 2023-01~2025-08 的"干净解析"具有欺骗性 —— 代码看起来是对的，只是那段时间没有第二个合约。

### 危害

不按合约过滤、只靠"按时间戳去重保留第一条"，会**随机混入日内价**：同一天里有些小时是日前价、有些是日内价，
序列看起来完全正常（价格量级合理、无缺失），但**价差噪声被静默注入**。日尺度统计（负价小时数、缺口弹性）会被污染。

### 正确解析

```python
# 解析时把 contract_MarketAgreement.type 带出来
elif n == "contract_MarketAgreement.type":
    contract = (ch.text or "").strip()

# 日前价只取 A01
if df["contract"].notna().any():
    df = df[df["contract"] == "A01"]
df = df.drop_duplicates("datetime_utc", keep="first")
```

### 校验（本流程实测）

过滤 A01 后，与 PS-029 的**一手 OMIE 原始文件**逐日比对 **2024-04-29**：

| 指标 | ENTSO-E（本次） | 一手 OMIE |
|---|---|---|
| 日均 | **58.27** | **58.27** |
| 最低 | **35.00** | **35.00** |
| 最高 | **102.26** | **102.26** |

三者完全一致 ⇒ 合约过滤正确，且 **ENTSO-E 的小时时间戳与 OMIE 的"小时序号"口径一致（均为时段起点，无需平移）**。
年度负价小时：2023 = 0（与 PS-031 一致）、2024 = **247**（与 PS-031 完全一致）、2025 = 557（PS-031 Energy-Charts 口径 544，差 13 h 源于 15 min 任一格为负即计该小时）。

### 避坑建议（陷阱二）

1. **必须按 `contract_MarketAgreement.type` 过滤**；只靠域名/分辨率/时间去重都不够。
2. **跨 2025-09 的序列要特别小心**：此前无 A07、此后有，同一份代码在前后两段表现不同。
3. 输出里保留合约维度，或在解析层就显式过滤并记录选择（本例取日前 A01）。
4. 用**独立数据源**（OMIE 原始文件）对已知日期的日/最低/最高三项同时校验 —— 只比日均可能掩盖混装。
